# I18n Design for Dashboard (zh-CN default, en-US optional)

## Summary
Adopt `next-intl` for the Next.js App Router to internationalize the entire WebUI and API responses.
Default locale is `zh-CN`, with `en-US` as a secondary locale. Locale selection is stored in a cookie
and can be switched via a UI control. Technical terms and product names remain in English.

## Goals
- Translate all WebUI text into Chinese while keeping English available.
- Return localized API error/messages based on request locale.
- Keep routes unchanged (no `/en` prefix) to minimize churn.
- Preserve external/raw logs unchanged, while local UI/log labels are localized.

## Non-Goals
- Translating third-party provider logs or external service responses.
- Restructuring routes or introducing locale prefixes.
- Changing data models beyond what is needed for message keys.

## Key Decisions
- Library: `next-intl` for App Router compatibility and SSR support.
- Locales: `zh-CN` (default) and `en-US`.
- Locale resolution order: cookie > `Accept-Language` > `zh-CN`.
- UI language switch: a top-level switch that sets cookie and refreshes.
- Message keys: stable semantic keys (e.g., `errors.auth.unauthorized`).

## Architecture
1. `dashboard/src/messages/{zh-CN,en-US}.json` store translation dictionaries.
2. `dashboard/src/i18n/request-locale.ts` resolves locale from cookie/header.
3. `dashboard/src/i18n/get-translations.ts` wraps `next-intl` server helpers.
4. App `layout.tsx` provides `NextIntlClientProvider` using server messages.
5. API routes use a shared response helper to emit `messageKey` + localized `message`.

## UI Language Switch
- Add a switch in `dashboard-nav` (or user menu).
- Switching calls `/api/i18n/locale` to set cookie, then `router.refresh()`.
- Cookie name: `cliproxyapi_locale` (long-lived, HTTP-only when possible).

## API / Errors / Notifications
- Standardize API responses to include `{ ok, messageKey, message, data }`.
- Server computes `message` using locale from the request.
- Client can re-render using `messageKey` if needed.

## Logs
- Internal audit/system events: store structured event types and values.
- UI renders localized labels/messages for these event types.
- External/raw service logs are displayed verbatim.

## Files to Touch (Expected)
- `dashboard/src/app/layout.tsx`
- `dashboard/src/app/api/**` (response helpers + locale handling)
- `dashboard/src/components/**` (replace literals with `t()`)
- `dashboard/src/messages/zh-CN.json`
- `dashboard/src/messages/en-US.json`
- `dashboard/src/i18n/**`

## Migration Plan (High Level)
1. Add `next-intl` and base i18n scaffolding.
2. Add locale resolution + language switch API/UX.
3. Replace UI literals with translation keys.
4. Convert API errors/messages to `messageKey` + localized text.
5. Verify zh-CN default + en-US switch.

## Testing Plan
- Unit: ensure translation keys exist in both locales.
- API: request with `Accept-Language: en` returns English message.
- UI: smoke test key pages render translated strings and switch works.

## Risks
- Missing keys or inconsistent phrasing across modules.
- API routes that currently emit raw strings without a standard response shape.
